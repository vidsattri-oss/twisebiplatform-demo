Angular BI Prototype · API Contract

What a .NET (or any) backend must implement

The Angular app talks to this API and nothing else — it doesn't know or care what language serves it. This page is the human-readable companion to docs/api/openapi.yaml, the authoritative, machine-readable contract a .NET team can implement or code-generate against without ever seeing this repo.

The one invariant that must survive porting

Every endpoint touching a connectionId/table/column must resolve those identifiers against the source's live schema before using them in a query — never a hardcoded list, never client text interpolated into SQL. Filter values are always bound parameters. This "metadata-validation gate" is the one security control the whole platform depends on. The mechanism is free to change per stack (ADO.NET GetSchema(), EF Core metadata, INFORMATION_SCHEMA queries) — the guarantee it provides may not.

Three of the six BI features run entirely in the Angular app and only ever call the generic query/schema endpoints below — there's nothing feature-specific to port for them.

Doing the port

Porting checklist for .NET

  1. Implement against the OpenAPI spec, not this page. docs/api/openapi.yaml is the source of truth — import it into NSwag or AutoRest to generate ASP.NET Core controller interfaces and DTOs directly, rather than hand-transcribing routes.
  2. Reuse ADO.NET's provider abstraction for connectivity. .NET already has a universal DbProviderFactory/DbConnection model — a better fit for a multi-source connection registry than the hand-rolled one here, which exists only because Node has no equivalent.
  3. Put secrets behind an interface, not a specific algorithm. Define ISecretStore as the port; let the host app supply an adapter to whatever it already uses (Key Vault, Data Protection API, an existing credentials table) instead of assuming AES-GCM from scratch.
  4. Configure camelCase JSON explicitly. ASP.NET Core's System.Text.Json defaults to PascalCase; every TypeScript interface the Angular app parses is camelCase. Set JsonNamingPolicy.CamelCase or every response silently fails to bind.
  5. Redesign the two SQLite-specific mechanisms deliberately, not accidentally. Cross-connection joins (ATTACH DATABASE) and per-upload dynamic table creation both need a real design decision for a production DB engine — see the porting notes inline above. The request/response contracts don't change; only how each is fulfilled does.
