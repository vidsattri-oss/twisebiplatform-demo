Part 1

End-to-end flow, at two scales

The local demo and the documented production target share one security pattern — every identifier in a query resolves against a live schema, never free text, and every trust boundary is drawn explicitly rather than assumed.

01 — As-built (this demo)

Angular SPA → Express BFF → SQLite

Everything below runs on one machine. The metadata validation gate is the load-bearing security control — it is what makes the rest of the boundary drawing possible.

Same validation-gate pattern — Cube.dev, not hand-written code, does the work once this scales past a local demo.

02 — Production target (documented, not yet built)

Angular SPA → Cube.dev → AWS RDS

The BFF's hand-written validation gate is replaced by Cube.dev's schema — same shape, proven engine. Non-CDC sources land through scheduled adapters instead of a live query path.

* SAP/ERP connector is planned (OData default, RFC fallback) — not yet built. See tracker item 01.

THE CONSTANT

The gate never trusts the client

Table and column identifiers are validated against a live schema — never free text into SQL. Filter values are always bound parameters. This holds identically whether the gate is hand-written (demo) or Cube.dev's schema (production).

What scales up

  • SQLite → RDS SQL Server
  • Hand-written gate → Cube.dev schema
  • None → IAM least-privilege DB role
  • Live-only → + scheduled ingestion adapters

What stays out of scope

Auth, multi-tenant row-level security, and a production deployment are explicitly not shown — this diagram covers the query path only, per the feasibility tracker's documented boundaries.

Part 2

What a .NET (or any) backend must implement

The Angular app talks to this API and nothing else — it doesn't know or care what language serves it. The authoritative, machine-readable version of this contract is docs/api/openapi.yaml, importable into NSwag/AutoRest to code-generate ASP.NET Core controllers and DTOs directly.

The one invariant that must survive porting

Every endpoint touching a connectionId/table/column must resolve those identifiers against the source's live schema before using them in a query — never a hardcoded list, never client text interpolated into SQL. Filter values are always bound parameters. This "metadata-validation gate" is the one security control the whole platform depends on — it's the same control called out as Part 1's "constant." The mechanism is free to change per stack (ADO.NET GetSchema(), EF Core metadata, INFORMATION_SCHEMA queries) — the guarantee it provides may not.

Scope the effort correctly first

Half of this needs no backend work at all

Three of the six BI features run entirely in the Angular app and only ever call the generic query/schema endpoints below — there's nothing feature-specific to port for them.

Already 100% portable

  • DAX-like formula editorjsep AST parser/evaluator — runs client-side, zero backend dependency
  • Custom visual renderingNative SVG/CSS bar/line/pie/table — zero backend dependency
  • Cross-filtering & the dashboard filter barPure Angular signal state — only calls the generic schema/distinct/range endpoints, doesn't care who serves them

Needs a real .NET implementation

  • Connectivity (feature 01)Connection registry, schema introspection, secrets
  • Ingestion (feature 02)Turning flattened rows into a queryable table
  • Filter-value discovery (feature 05)Distinct-values and min/max endpoints behind the same schema gate as 01

Doing the port

Porting checklist for .NET

  1. Implement against the OpenAPI spec, not this page. docs/api/openapi.yaml is the source of truth — import it into NSwag or AutoRest to generate ASP.NET Core controller interfaces and DTOs directly, rather than hand-transcribing routes.
  2. Reuse ADO.NET's provider abstraction for connectivity. .NET already has a universal DbProviderFactory/DbConnection model — a better fit for a multi-source connection registry than the hand-rolled one here, which exists only because Node has no equivalent.
  3. Put secrets behind an interface, not a specific algorithm. Define ISecretStore as the port; let the host app supply an adapter to whatever it already uses (Key Vault, Data Protection API, an existing credentials table) instead of assuming AES-GCM from scratch.
  4. Configure camelCase JSON explicitly. ASP.NET Core's System.Text.Json defaults to PascalCase; every TypeScript interface the Angular app parses is camelCase. Set JsonNamingPolicy.CamelCase or every response silently fails to bind.
  5. Redesign the two SQLite-specific mechanisms deliberately, not accidentally. Cross-connection joins (ATTACH DATABASE) and per-upload dynamic table creation both need a real design decision for a production DB engine — see the porting notes inline above. The request/response contracts don't change; only how each is fulfilled does.
