Angular BI Prototype · Implementation Summary

How each of the six features was actually solved

This is an archival summary of the earlier Angular prototype. The current v3 implementation and acceptance checks are in docs/architecture.md and the repository README.

01 Multiple data source connectivity Live

Solution leveraged

A real connection registry (connections.js) backed by SQLite files, with every table/column validated dynamically via PRAGMA table_info — no hardcoded table list, so a new connection becomes queryable with zero code changes. Proved this by standing up a second database (sales.db, a software company's customers/deals/invoices) and connecting it live through a new "Add Connection" UI restricted to files the server already knows about. Cross-connection joins work for real via SQLite's ATTACH DATABASE — verified against an injection attempt, and the fan-out risk of joining on a shared dimension (region) rather than a unique key is surfaced directly in the UI, not hidden. Credential encryption (secrets.js, AES-256-GCM) is wired in even though SQLite doesn't need it yet.

  • The join mechanism doesn't generalize. ATTACH DATABASE only works because both sides are SQLite files in the same process — it cannot join a real SQL Server source to Oracle, or to SAP, in the same query. A real heterogeneous join needs a federation layer (Cube.dev) or an ETL/staging step; "swap the resolver" understates that this is a different architecture, not a driver swap.
  • No real enterprise driver exists yet — only SQLite is actually implemented. SQL Server/Oracle/SAP adapters, connection pooling, and retry/timeout handling are all unbuilt.
  • No RBAC or row-level security — any user of the app sees every registered connection and every table in it. The actual requirement (a company-wide BI platform) needs per-user/per-role data access, which isn't modeled at all.
  • Key management is dev-only — secrets.js falls back to an ephemeral in-memory key with a loud warning if CONNECTION_SECRET_KEY isn't set; production needs a real KMS/HSM-backed key with rotation.
  • "Near real-time" isn't actually met at scale — every chart runs a live synchronous query on load/click. Fine for demo-sized SQLite files; the seconds-level freshness target from the original requirement needs a caching or materialized-view layer this prototype doesn't have.
When a real networked source (SQL Server, SAP) replaces a second SQLite file, swap the connection resolver for the documented Cube.dev/RDS path — the Angular-facing contract (list connections, get schema, run query) doesn't change. SAP/ERP is the one source still fully gated behind its own connector build (OData default, RFC fallback, per the tracker).
02 JSON parsing and flattening Live

Solution leveraged

A pure client-side Angular service (FlattenService) doing recursive dotted/bracketed-path flattening, unit-tested including edge cases (empty objects/arrays, null leaves). Extended this session into a real ingestion pipeline: flattened rows post to /api/ingest, which dynamically creates a sanitized SQL table and inserts via parameterized statements — from the seeded demo events, from any already-connected table, or from an uploaded .json/.csv file. The result is immediately a real, queryable table, not just a preview.

  • Runs on the main thread — a large payload will visibly freeze the UI; there's no Web Worker yet, so "flatten a real API export" (often tens of MB) isn't actually safe today.
  • No schema evolution. Each ingest infers a table shape from that moment's data; a second upload with new or renamed fields has no reconciliation path — it either fails or drifts silently. A real ingestion pipeline needs versioned schemas.
  • CSV parsing is naive — no handling for quoted commas, embedded newlines, or encoding edge cases. Real-world CSV exports (e.g., from SAP or Excel) will break it.
  • No dedup or upsert — every ingest is a full insert; re-running the same import duplicates rows. The actual requirement (repeatable ingestion, not one-off demo imports) needs idempotency.
  • No data-quality or lineage tracking — no required-field validation, type-coercion reporting, or audit trail of what was ingested, when, and by whom, which a governed BI platform needs.
Move flattening into a Web Worker once payloads exceed the ~1–10MB threshold already documented. If this becomes a repeated ingestion path rather than one-off imports, add basic schema-evolution handling for new columns appearing in a later upload.
03 DAX-like formula editor Partial — highest risk

Solution leveraged

A real jsep-based AST parser/evaluator (FormulaService) for arithmetic over saved measures — unit-tested specifically to prove it fails closed on an unknown measure reference and never evaluates via eval()/Function(). The CALCULATE-style filter-context half is an explicit, clearly labeled placeholder panel in the UI, not something quietly approximated with the wrong semantics.

  • No context manipulation — arguably DAX's defining feature is entirely missing. CALCULATE-style filter-context override (e.g., "total sales ignoring the region filter") is a placeholder, not functional. Without it, this isn't a DAX-equivalent yet, just a calculator over pre-built numbers.
  • No time intelligence — no SAMEPERIODLASTYEAR/TOTALYTD/rolling-average equivalents, which are near-universal asks for an operations dashboard (month-over-month, YoY).
  • No cross-source formulas — a formula still can't combine a measure from Operations with one from Sales in a single expression; each side must already exist as a separately-built, pre-aggregated measure. This was an explicit early requirement ("formulas should support cross-source joins too") that isn't met.
  • Can't express its own aggregation — the evaluator only combines numbers already computed by other queries; it can't itself define "SUM(x)/SUM(y) grouped by region" as one dynamic, re-evaluating formula the way DAX measures do.
Still the single largest schedule risk on the tracker. Before investing further in the client-side formula UI, spike Cube.dev (or Malloy) against 3–4 real cross-source formulas to validate the semantic-layer approach — the AST-parsing, no-eval() pattern built here should carry over unchanged to whatever real engine replaces the demo backend.
04 Custom visual extensibility Live

Solution leveraged

Native SVG/CSS rendering for Bar, Line, and Pie — no charting-library dependency. This session added a fourth type, Table, the exact same way: one more entry in the chart-type switch and one more rendering branch, no architectural change required. That's the actual proof the rendering layer is swappable independent of the query/data layer, not just a claim.

  • Not actually extensible by anyone but this codebase's developers. There's no plugin architecture — adding a visual means editing source and rebuilding/redeploying the whole app. A third party (or a less-technical internal team) can't add one, which is what "extensibility" usually implies.
  • No map visual — a real gap for an oilfield/drilling company where rig and site geography is often the most natural way to view operations data; only 4 chart-shaped types exist, nothing geospatial.
  • No complex/combo visuals — gauges, funnels, combo (bar+line), or custom D3 visuals aren't supported.
  • Not built for scale or accessibility — no virtualization/binning for large category counts, and no screen-reader/keyboard-navigation support in the hand-rolled SVG.
Adding 1–2 more native types (scatter, gauge) is low-risk and would round out coverage before investing in a full plugin SDK (Module/Native Federation) for genuinely third-party visuals — that remains a bigger, separate effort.
05 Filters Partial by design

Solution leveraged

Field/operator/value filter rows plus Group By, validated server-side against the live schema with bound parameters — no client-supplied identifier reaches SQL unescaped. A capability-status chip row is honest about scope: Top N, Relative Date, Boolean, and Cascading filters are shown as explicit placeholders, never silently missing.

  • Four common filter types don't work yet — Relative Date ("last 30 days"), Top N, Boolean toggles, and Cascading (dependent) filters are all placeholders. These are near-baseline expectations in any Power BI-comparable tool, not edge cases.
  • No report-level slicers. Filters live per-chart in Query Builder; there's no shared, page-level filter widget a user sets once that every visual on a dashboard respects (cross-filter-by-click is a different mechanism, not a substitute).
  • Can't filter on a calculated field — only raw table columns are filterable, not a formula/ratio result.
  • No typeahead/search for high-cardinality fields — a plain <select> doesn't scale to filtering on, say, a customer name across thousands of rows.
Relative Date and Top N are the best next additions — both are pure SQL transformations (date math, ORDER BY/LIMIT) needing no new infrastructure, unlike Cascading filters, which depend on the same relationship metadata the formula editor is already waiting on.
06 Cross-filtering Live

Solution leveraged

A connection+table-scoped SelectionService (an Angular signal) — generalized this session from "same Group By" to "same table," so clicking one chart's dimension filters every chart querying that table, not only ones grouped identically. Extended with a real Table visual as the "linked filters" surface (Power BI's table/matrix pattern), addable from the Query Builder exactly like any other chart type, plus a quick-peek drill-down modal — both reading the same shared selection state, verified end to end in the browser.

  • Single selection only — picking a second data point replaces the filter instead of adding to it. Power BI supports multiple simultaneous highlighted selections (Ctrl+click); this doesn't yet.
  • No real relationship model — this is the biggest structural gap. Cross-filtering only fires when two charts query the literal same table name. Two visuals on genuinely related tables (e.g., crews and the equipment assigned to them) do NOT filter each other, because there's no foreign-key/relationship metadata — the mechanism that makes Power BI's cross-filtering actually powerful across a whole data model, not just within one table.
  • No cross-dashboard persistence — a selection clears on navigating away or reloading; there's no bookmarking or shareable filtered-view URL.
  • Table visuals are filter receivers only — clicking a table row doesn't set a selection, so the linkage is one-directional, not the full symmetric model the original ask implied.
  • No highlight-vs-filter distinction — Power BI can dim non-matching data (highlight) or remove it entirely (filter) as separate modes; this only ever removes.
Multi-select (Ctrl+click) was deliberately left out this round. Also worth a deliberate decision on whether Table visuals should become filter sources (a row click driving selection), not just receivers, if bidirectional cross-filtering turns out to matter for this audience.

  • Zero actual functionality — and likely the most expensive item to build for real. "Placeholder" understates the gap: a working version needs an LLM integration, a security review for what data gets sent to a model, per-query cost, and hallucination guardrails before it could safely sit in front of real operations/sales data. Beyond any single feature

Limitations the demo doesn't surface per-feature

  • No authentication or authorization anywhere in the app. Every connection, table, and dashboard is visible to anyone who can reach the URL — there's no login, no roles, no row-level security. This is the single biggest gap between "working prototype" and "something a company deploys."
  • Single-process, file-based backend. The Express server and SQLite files on disk can't be horizontally scaled or load-balanced the way a production BI backend needs — one process, one machine, one set of files.
  • No caching, monitoring, or automated backup. Every dashboard load is a live query against source; there's no health/alerting instrumentation and no backup strategy for the SQLite files, which currently are the only copy of demo data.
  • Real-time freshness is demonstrated at demo scale only. The original requirement was seconds-level freshness; that holds here because the data is tiny. Nothing in this build has been tested against production-scale tables or concurrent users.

Where to spend the next cycle

Overall recommendations

  1. Add authentication and role-based access before any real deployment. Every limitation above compounds this one — there's currently no login and no per-user data access at all, which blocks a real rollout regardless of how complete any single feature is.
  2. Build the SAP/ERP connector. It's the one remaining gap in item 01 — everything else in connectivity is live. OData default, RFC fallback, per the plan already in the tracker.
  3. Spike Cube.dev against real formulas. Item 03 is the highest schedule risk on the whole tracker. Validate the semantic-layer approach on 3–4 real cross-source formulas before building more UI around it.
  4. Add Relative Date and Top N filters. Cheapest, highest-value gap in item 05 — pure SQL, no new infrastructure, unlike Cascading filters which need relationship metadata that doesn't exist yet.
  5. Decide on multi-select and table-as-source. Both are real scope decisions for item 06, not technical blockers — worth a deliberate yes/no rather than defaulting.
  6. Keep the metadata-validation gate as the one non-negotiable pattern. Every item above depends on it staying intact as real sources replace SQLite — it's what makes items 01, 03, 05, and 06 safe to extend without re-litigating security each time.
