Angular BI Prototype · Implementation Summary

How each of the six features was actually solved

Not the plan — what got built, tested, and verified working in the running prototype this session, plus what to do next for each.

01 Multiple data source connectivity Live

Solution leveraged

A real connection registry (connections.js) backed by SQLite files, with every table/column validated dynamically via PRAGMA table_info — no hardcoded table list, so a new connection becomes queryable with zero code changes. Proved this by standing up a second database (sales.db, a software company's customers/deals/invoices) and connecting it live through a new "Add Connection" UI restricted to files the server already knows about. Cross-connection joins work for real via SQLite's ATTACH DATABASE — verified against an injection attempt, and the fan-out risk of joining on a shared dimension (region) rather than a unique key is surfaced directly in the UI, not hidden. Credential encryption (secrets.js, AES-256-GCM) is wired in even though SQLite doesn't need it yet.

When a real networked source (SQL Server, SAP) replaces a second SQLite file, swap the connection resolver for the documented Cube.dev/RDS path — the Angular-facing contract (list connections, get schema, run query) doesn't change. SAP/ERP is the one source still fully gated behind its own connector build (OData default, RFC fallback, per the tracker).
02 JSON parsing and flattening Live

Solution leveraged

A pure client-side Angular service (FlattenService) doing recursive dotted/bracketed-path flattening, unit-tested including edge cases (empty objects/arrays, null leaves). Extended this session into a real ingestion pipeline: flattened rows post to /api/ingest, which dynamically creates a sanitized SQL table and inserts via parameterized statements — from the seeded demo events, from any already-connected table, or from an uploaded .json/.csv file. The result is immediately a real, queryable table, not just a preview.

Move flattening into a Web Worker once payloads exceed the ~1–10MB threshold already documented. If this becomes a repeated ingestion path rather than one-off imports, add basic schema-evolution handling for new columns appearing in a later upload.
03 DAX-like formula editor Partial — highest risk

Solution leveraged

A real jsep-based AST parser/evaluator (FormulaService) for arithmetic over saved measures — unit-tested specifically to prove it fails closed on an unknown measure reference and never evaluates via eval()/Function(). The CALCULATE-style filter-context half is an explicit, clearly labeled placeholder panel in the UI, not something quietly approximated with the wrong semantics.

Still the single largest schedule risk on the tracker. Before investing further in the client-side formula UI, spike Cube.dev (or Malloy) against 3–4 real cross-source formulas to validate the semantic-layer approach — the AST-parsing, no-eval() pattern built here should carry over unchanged to whatever real engine replaces the demo backend.
04 Custom visual extensibility Live

Solution leveraged

Native SVG/CSS rendering for Bar, Line, and Pie — no charting-library dependency. This session added a fourth type, Table, the exact same way: one more entry in the chart-type switch and one more rendering branch, no architectural change required. That's the actual proof the rendering layer is swappable independent of the query/data layer, not just a claim.

Adding 1–2 more native types (scatter, gauge) is low-risk and would round out coverage before investing in a full plugin SDK (Module/Native Federation) for genuinely third-party visuals — that remains a bigger, separate effort.
05 Filters Partial by design

Solution leveraged

Field/operator/value filter rows plus Group By, validated server-side against the live schema with bound parameters — no client-supplied identifier reaches SQL unescaped. A capability-status chip row is honest about scope: Top N, Relative Date, Boolean, and Cascading filters are shown as explicit placeholders, never silently missing.

Relative Date and Top N are the best next additions — both are pure SQL transformations (date math, ORDER BY/LIMIT) needing no new infrastructure, unlike Cascading filters, which depend on the same relationship metadata the formula editor is already waiting on.
06 Cross-filtering Live

Solution leveraged

A connection+table-scoped SelectionService (an Angular signal) — generalized this session from "same Group By" to "same table," so clicking one chart's dimension filters every chart querying that table, not only ones grouped identically. Extended with a real Table visual as the "linked filters" surface (Power BI's table/matrix pattern), addable from the Query Builder exactly like any other chart type, plus a quick-peek drill-down modal — both reading the same shared selection state, verified end to end in the browser.

Multi-select (Ctrl+click) was deliberately left out this round. Also worth a deliberate decision on whether Table visuals should become filter sources (a row click driving selection), not just receivers, if bidirectional cross-filtering turns out to matter for this audience.
— AI mode Placeholder, as instructed

Solution leveraged

A static, clearly labeled example — no live model call, no backend request. Kept this way per explicit instruction, so the demo never implies a capability that isn't there.

Where to spend the next cycle

Overall recommendations

  1. Build the SAP/ERP connector. It's the one remaining gap in item 01 — everything else in connectivity is live. OData default, RFC fallback, per the plan already in the tracker.
  2. Spike Cube.dev against real formulas. Item 03 is the highest schedule risk on the whole tracker. Validate the semantic-layer approach on 3–4 real cross-source formulas before building more UI around it.
  3. Add Relative Date and Top N filters. Cheapest, highest-value gap in item 05 — pure SQL, no new infrastructure, unlike Cascading filters which need relationship metadata that doesn't exist yet.
  4. Decide on multi-select and table-as-source. Both are real scope decisions for item 06, not technical blockers — worth a deliberate yes/no rather than defaulting.
  5. Keep the metadata-validation gate as the one non-negotiable pattern. Every item above depends on it staying intact as real sources replace SQLite — it's what makes items 01, 03, 05, and 06 safe to extend without re-litigating security each time.
