End-to-end flow, at two scales

The local demo and the documented production target share one security pattern — every identifier in a query resolves against a live schema, never free text, and every trust boundary is drawn explicitly rather than assumed.

01 — As-built (this demo)

Angular SPA → Express BFF → SQLite

Everything below runs on one machine. The metadata validation gate is the load-bearing security control — it is what makes the rest of the boundary drawing possible.

Same validation-gate pattern — Cube.dev, not hand-written code, does the work once this scales past a local demo.

02 — Production target (documented, not yet built)

Angular SPA → Cube.dev → AWS RDS

The BFF's hand-written validation gate is replaced by Cube.dev's schema — same shape, proven engine. Non-CDC sources land through scheduled adapters instead of a live query path.

* SAP/ERP connector is planned (OData default, RFC fallback) — not yet built. See tracker item 01.

THE CONSTANT

The gate never trusts the client

Table and column identifiers are validated against a live schema — never free text into SQL. Filter values are always bound parameters. This holds identically whether the gate is hand-written (demo) or Cube.dev's schema (production).

What scales up

  • SQLite → RDS SQL Server
  • Hand-written gate → Cube.dev schema
  • None → IAM least-privilege DB role
  • Live-only → + scheduled ingestion adapters

What stays out of scope

Auth, multi-tenant row-level security, and a production deployment are explicitly not shown — this diagram covers the query path only, per the feasibility tracker's documented boundaries.
